anna-app APS Files Demo

Saves text notes to Anna object storage two different ways — pick one with the toggle below:

  • Tool invoke — the app calls anna.tools.invoke against a bundled Executa that owns the aps.files capability and does the files/* reverse-RPC. The app needs no files grant. Writes to scope=user (user-wide, default) or scope=tool (plugin-private) — pick below. (Recommended best practice.)
  • HOST API — the app calls anna.files.* directly with its own ui.host_api.files grant: upload_init → browser PUT to a presigned R2 URL → upload_finalize, plus the host-mediated files.download browser save. Writes to scope=app (the app's own object space).
Executa scope:

Run with anna-app dev --storage aps (real account). Without it, saves return a clean not_implemented (-32004). Note: each scope is an isolated bucket (user / tool / app), so a note saved under one scope is not listed by another. HOST API uploads also require the storage bucket to allow CORS from this origin (configured in production).

Get link mints a short-lived presigned URL for the path above. Download calls anna.files.download — the host-mediated save: the host presigns with Content-Disposition: attachment, triggers the browser save dialog from the top-level page, and strips the URL before this iframe sees the result. The bearer URL never enters app DOM. In Tool invoke mode with scope=user the app passes scope: "user" — gated by the manifest capability aps.scope.user.read. With scope=tool the object is plugin-private, so the app-side files.download is not available — the demo asks the Executa for a presigned link instead. In HOST API mode it reads the app's own scope=app object.
